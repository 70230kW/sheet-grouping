# 設計メモ（要確認事項を含む）

このドキュメントは「手戻りが大きい部分」の判断材料として、実装した初期案と代替案をまとめたものです。
確認・変更が必要な項目は **[要確認]** と記しています。

## 1. Google スプレッドシート連携の認証方式 **[要確認]**

デプロイ先が Firebase Hosting（静的サイト・サーバー無し）なので、ブラウザだけで完結する方式を採用しました。

| 方式 | 採用 | 概要 | Google Cloud 側の設定 | 備考 |
|---|---|---|---|---|
| **A. OAuth（Google Identity Services）** | **推奨・実装済** | 利用者が自分の Google アカウントでログインし、読み取り専用トークンでシートを読む | プロジェクト作成 / Sheets API 有効化 / OAuth 同意画面 / OAuth クライアント ID（Web） | シートは通常の共有設定のままで可。秘密情報を配布しない。テストユーザー登録 or Workspace 内部アプリ設定が必要 |
| B. API キー | 実装済（切替可） | API キーのみで読む | Sheets API 有効化 / API キー作成（HTTP リファラ制限） | シートを「リンクを知っている全員が閲覧可」にする必要あり。会員企業の情報を載せるシートには **非推奨** |
| C. サービスアカウント | 未実装 | サーバー側で鍵を保持して読む | サービスアカウント + 鍵 + Cloud Functions 等のバックエンド | ブラウザに鍵を置けないため Cloud Functions が必要。設定・運用コストが最も高い |

**A を採用した理由**: サーバー不要、鍵の漏洩リスク無し、シートの共有設定を変えずに済む。
Firebase Hosting 上で動かす場合、OAuth クライアントの「承認済み JavaScript 生成元」に
`https://<project>.web.app` と `http://localhost:5173` を登録するだけで動作します。

> 貴社の Google Workspace で「内部アプリ」として公開できれば同意画面の審査は不要です。
> 個人 Gmail アカウントの場合は「テストユーザー」に自分のアドレスを登録すれば利用できます（最大 100 名）。

手順は `docs/SETUP.md` を参照してください。

## 2. カラム設計 **[要確認]**

列名はアプリ内「設定 > 列マッピング」で変更でき、部分一致で解決します（例: 設定 "商圏" でヘッダー "所在地・商圏エリア" に一致）。
初期値は次の通りです。

| 項目 | 初期ヘッダー名 | 形式 | 使われ方 |
|---|---|---|---|
| 会社名 | 会社名 | 文字列（必須） | 表示・ID |
| 業態 | 業態 | 「、」「/」「・」区切りで複数可。**先頭が主業態** | 多様性・偏り判定、他社の「繋げたい」「やりたい」とのマッチ対象 |
| 売上規模 | 売上規模 | ランク（S/A/B/C/D）または数値（億円。「12億」「3.5億円」「1,200百万円」可） | レベル 0〜4 に変換し、差をペナルティに使用 |
| 所在地・商圏エリア | 所在地・商圏エリア | 区切りで複数可（例: 北海道・札幌） | トークン **完全一致** で商圏重複と判定 |
| 今後やりたい事業 | 今後やりたい事業 | タグ or 自由記述（区切りで分割） | 他社の業態と部分一致で親和性加点 |
| 繋げたい企業・業種 | 繋げたい企業・業種 | タグ or 自由記述 | 他社の業態・強みと部分一致で加点 |
| 強み・特徴（任意） | 強み・特徴 | 自由記述 | 「繋げたい」のマッチ対象に追加 |
| 備考（任意） | 備考 | 自由記述 | 表示のみ |

**確認したい点**

1. 売上規模はランク表記か数値か。両方混在するか。ランクの段階数（5 段階で足りるか）
2. 商圏エリアの粒度（都道府県 / 市区町村 / 「関東」などの広域）。現状は完全一致なので「東京」と「東京都」は別扱いです。
   実データの表記ゆれが大きい場合は、都道府県への正規化辞書を追加します。
3. 「やりたい事業」「繋げたい企業」が自由記述の場合、部分一致だけでは拾えない表現（例: 「EV 充電」と「レンタカー」）があるはずです。
   その場合は **業態同士の親和性テーブル**（例: やりたい「カーシェア」→ 業態「IT」「レンタカー」）を設定画面で編集できるようにする案があります。
4. 1 社複数名参加の扱い（同じ会社を同島に固定するか、別行として扱うか）

## 3. スコアリングモデル（初期案）**[相談しながら調整]**

島スコア = Σ(ペアスコア) + 島全体スコア、全体スコア = Σ(島スコア)。値が大きいほど良い配置です。

### ペアごと（島内の全 2 社の組み合わせ）

| 項目 | 初期値 | 計算 |
|---|---|---|
| 同一商圏ペナルティ | −30 | エリアトークンが 1 つでも完全一致 |
| 売上規模ギャップ | −8 × (レベル差 − 許容差) | 許容差 初期 1（隣接ランクは無罰） |
| 極端な乖離 追加ペナルティ | −20 | レベル差 ≥ 3 のとき上記に加算 |
| 繋げたい企業マッチ | +12 × 件数 | A の「繋げたい」 ⊂ B の業態/強み（双方向で評価） |
| やりたい事業 親和性 | +6 × 件数 | A の「やりたい」 ⊂ B の業態（双方向） |

### 島全体

| 項目 | 初期値 | 計算 |
|---|---|---|
| 業態多様性 | +4 × (ユニーク主業態数 − 1) | 6 社 4 業態なら +12 |
| 業態偏り | −10 × (最多業態の社数 − 過半数) | 6 社中 4 社が同業態なら −10 |

**バランスの考え方**: 商圏重複 1 ペア（−30）は「繋げたいマッチ 2〜3 件」で相殺される水準。
D×S のような極端な売上差（−8×3−20 = −44）は商圏重複より強く嫌う。
「絶対に同席させない」制約にしたい項目は重みを 100 以上にすれば実質ハード制約になります。

### アルゴリズム

1. **貪欲法**: 「配置しにくい参加者」（同一商圏の相手が多い・売上が平均から離れている）から順に、
   追加時のスコア増分が最大の島へ入れる。
2. **局所探索**: 島間の 2 社入れ替え（swap）と 1 社移動（move）で全体スコアが改善する限り繰り返す。
3. **ランダムリスタート**: 上記を N 回（初期 8 回）実行し最良解を採用。
4. 🔒 で固定した島は再配置の対象外。「現在の配置を改善」は手動配置を起点に 2 のみ実行。

計算量は 30 社 × 5 島程度なら数十 ms です。

## 4. 画面フロー

1. **データ**: シート読み込み / 貼り付け / サンプル → 取り込み結果テーブル（売上レベル判定不能を警告）
2. **座席表**: 島カード + 未配置プール、D&D、島ごとのスコアと警告（赤=エリア重複・極端な売上差、黄=売上差・業態偏り）、
   島数・定員の変更、再生成、印刷
3. **設定**: Google 連携 / 列マッピング / 売上判定 / 重み

設定・データ・配置は localStorage に保存され、リロードしても残ります（ブラウザ単位）。
